## Research Question

The change `ai-toolkit-package` bundles three deliverables into one unit of work: an
npm package skeleton, the `code-review` skill + rules it carries, and the CI/CD
workflow that publishes it. Before planning, establish: what already exists here,
what the supplied specs and templates actually require, and which of their
assumptions break against *this* repo and *this* account.

This is a greenfield repo, so there is no codebase to trace. The research is
therefore (a) a close read of the four specs and five templates, (b) an empirical
check of the environment, and (c) the delta between the two.

## Summary

The templates are close to usable, but **four of their assumptions are false here**
and two of them are hard build failures, not stylistic nits:

1. **`npm ci` cannot run** — both workflow jobs call it, and it errors out with
   `EUSAGE` when there is no `package-lock.json`. The package has zero
   dependencies, so nothing generates a lockfile by accident. *Verified.*
2. **`postinstall` fires inside our own repo** — running `npm install` here (which
   is how a lockfile gets created, and what CI does) executes `install.js` with the
   project root resolving to the repo itself. It would write
   `.claude/skills/code-review/` and append a rules block to our own `CLAUDE.md`
   before `npm pack --dry-run` ever runs. *Verified.*
3. **Scope placeholder** — every template says `@twoj-zespol`; GitHub Packages
   requires the scope to equal the repo owner, `tomskoczewski`.
4. **"Merge to `main`" has no PR to merge** — the repo is literally empty, so the
   first push *creates* the default branch and is itself the publish trigger.

Everything else in the specs holds up. Auth needs no secret for publishing, the
account's token already carries `read:packages` for the Faza 18 smoke test, and
Node 22 locally is compatible with the `>=20` engine constraint the workflow pins.

### Blocker 1 — `npm ci` without a lockfile

Both the `validate` and `publish` jobs in
`configs/m5l4-github-packages-publish-ai-toolkit.yml.template` run `npm ci`
unconditionally. Reproduced against a minimal dependency-free `package.json`:

```
npm error code EUSAGE
npm error The `npm ci` command can only install with an existing package-lock.json or
npm error npm-shrinkwrap.json with lockfileVersion >= 1.
```

This is not conditional on having dependencies — `npm ci` refuses on the missing
file alone. Two ways out:

- **Commit a `package-lock.json`.** Honest for a published package, keeps `npm ci`,
  and matches what a consumer's toolchain expects. The lockfile for a zero-dependency
  package is ~7 lines.
- **Drop the install step entirely.** `npm pack --dry-run` and `npm publish` do not
  need `node_modules` when there are no dependencies.

Committing the lockfile is the better default: it keeps the workflow shaped like a
normal npm pipeline, so it stays correct the moment a dependency is added. Dropping
`npm ci` silently breaks later.

### Blocker 2 — `postinstall` self-installs into this repo

`install.js`'s `findProjectRoot()` walks up from `__dirname` looking for a
`node_modules` ancestor and **falls back to `process.cwd()`** when it finds none.
Inside a consumer that fallback never triggers. Inside our own repo it always does.
Reproduced with the template's exact resolution logic:

```
PROJECT_ROOT_RESOLVED: <package root>   # not a consumer — the package itself
```

So `npm install` in this repo — the very command that creates the lockfile — would:

- copy `skills/code-review/` into our own `.claude/skills/code-review/`
- append the managed rules block to our own root `CLAUDE.md`
- write our own `.claude/.ai-toolkit-manifest.json`

In CI the same thing happens before `npm pack --dry-run`, so the tree being packed
is not the tree that was checked out. It won't fail the build (the template wraps
`main()` in try/catch and only warns), but it is a silent correctness problem and it
dirties the working tree locally — which matters, because nothing here gets
committed without review.

Mitigations, in preference order:

1. **Guard `install.js`**: if no `node_modules` ancestor is found, treat it as
   "running inside the package itself" and no-op with a one-line notice. This keeps
   `npm install`, `npm ci`, and CI all clean, and costs about four lines.
2. Use `npm ci --ignore-scripts` in CI. Fixes CI only, not local installs.
3. Use the `bin` entry (`npx ai-toolkit`) for manual installs and drop `postinstall`.
   Deviates from the spec, which explicitly asks for `postinstall`.

Option 1 is the only one that fixes both surfaces without dropping a spec requirement.

### Blocker 3 — scope placeholder `@twoj-zespol`

GitHub Packages requires the npm scope to match the repository owner. The string
`@twoj-zespol` appears in **five** places across the supplied material, and every one
of them must become `@tomskoczewski`:

- `configs/…package.json.template` → `name`
- `configs/…install.js.template` → `PACKAGE_NAME` (which also generates the two
  sentinel markers — a stale value here means uninstall silently fails to find the
  block it is supposed to remove)
- `configs/…uninstall.js.template` → `PACKAGE_NAME` / sentinels
- `configs/…consumer.npmrc.template` → the registry mapping key
- `configs/…publish-ai-toolkit.yml.template` → `scope:` in **both** `setup-node` steps

The sentinel coupling is the sharp edge: `install.js` and `uninstall.js` each derive
`BEGIN`/`END` from their own local `PACKAGE_NAME` constant. If the two files ever
disagree, install writes one marker pair and uninstall looks for another.

### Blocker 4 — there is nothing to merge into `main`

The plan's Faza 17 step reads "merge to `main` → workflow publishes 0.1.0", but the
remote has no commits and no default branch. The realistic sequence is:

1. First push to `main` creates the default branch **and** matches the workflow's
   `on.push.branches: [main]` trigger.
2. That single push runs `validate` → `publish` and ships `0.1.0`.

So publication happens on the initial push, not on a PR merge. Worth knowing before
Faza 17, because it means the workflow file has to be correct *in that first push* —
there is no PR run to catch a typo first. The template's `pull_request` trigger will
simply never have fired by then.

(The `if: github.event_name == 'push'` guard on the `publish` job is still worth
keeping — it is what stops later PRs from publishing.)

### Authentication — publish vs. read

These are two different tokens and it is easy to conflate them.

- **Publishing (CI, Faza 17)** needs **no secret**. `permissions: packages: write`
  plus the automatic `secrets.GITHUB_TOKEN` is sufficient, and the token is scoped to
  this repo for the life of the job. Do not wire a PAT.
- **Reading (local smoke test, Faza 18)** does need a token, because a private repo
  yields a private package. The account token already carries `read:packages`, and
  `gh auth token` emits it. It is an OAuth token (`gho_`), not a classic PAT — which
  is the direction GitHub is pushing anyway.

One thing that cannot be checked ahead of time: the registry returns `404` for a
package that does not exist yet, regardless of whether the token is valid. So a
failed read before Faza 17 proves nothing, and read auth can only be verified once
`0.1.0` is actually up.

- `README.md` justifies GitHub Packages over CodeArtifact in 2–3 sentences

**Ours** (the lesson says so explicitly — templates are a starting point):

- exact package `description`, `license`, `repository` metadata
- whether to add a `repository` field (recommended: GitHub links the package to a repo
  from it, and it renders the source link on the Packages tab)
- how the skill's prose reads — it should review against *our* conventions, not restate
  the handout verbatim
- what goes in `rules/CLAUDE.md`
- how thorough `validate` is beyond the five spec-mandated checks
- whether the frontmatter-vs-directory-name check is a shell one-liner or a script

### The idempotency requirement has a subtlety

The spec asks for idempotence, and the template mostly delivers it two different ways:

- **skills**: `fs.rmSync(target, {recursive:true, force:true})` then re-copy — a full
  replace, so it is idempotent by construction, and it also removes files dropped
  between versions.
- **rules**: `applyRulesBlock()` splices between sentinels if both are present,
  otherwise appends. Idempotent *provided* the markers survive round-trips.

The gap: `writeManifest` overwrites `files` with only what the current run installed.
If v0.1.1 ships fewer files than v0.1.0, the older stragglers are neither removed by
install nor recorded for uninstall. Minor for this project (Faza 18's bump only edits
`SKILL.md`), but it is the kind of thing the Faza 18 double-install check is meant to
catch, so it should be a conscious decision rather than an oversight.

## Architecture Insights

- **The package is a content carrier, not a library.** Nothing is imported from it;
  the entire payload is markdown moved into place by a lifecycle script. That is why
  it has no dependencies, no build step, and no tests in the usual sense — and why
  `validate` asserts on *file shape* rather than on behavior.
- **Sentinel-delimited managed blocks are the whole idempotency story for rules.**
  The package owns the text between the markers and nothing else, so a consumer can
  hand-edit the rest of their `CLAUDE.md` freely. This only holds while the marker
  strings stay stable — changing the package name later would orphan every previously
  installed block.
- **`postinstall` is a blunt instrument.** It runs on every install everywhere, with
  no way to distinguish "installed as a dependency" from "developing the package"
  except by inspecting the path. The `node_modules`-ancestor probe is that inspection,
  and its fallback branch is where blocker 2 lives.
- **Failure policy is asymmetric on purpose.** `install.js` swallows its own errors so
  a broken toolkit never fails a consumer's `npm install`; `uninstall.js` does not.
  That asymmetry is correct and should be preserved.
